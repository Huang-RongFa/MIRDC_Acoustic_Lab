- 網站還沒有正式主機，目前用 Cloudflare 臨時通道測試。
- 臨時通道上的錄音網站不是本分支的版本：

  - 拒絕把輸出寫進 Git 儲存庫。

## 四、測試中發現並修正的判讀錯誤

原本打算在報告裡自動提示「可能有自動增益」：軌間位準差與整體響度的相關係數 ≥ 0.5 就提示。

合成資料的三軌增益是固定的，相關係數卻高達 0.97–0.99：
- 前 3 秒停機時，各軌只剩各自的底噪，位準差接近 0；
- 運轉時位準差等於增益差；
- 所以位準差一定跟著響度變。

因此這個指標不能單獨用來判斷自動增益。處理方式：

- 移除自動提示，只列出數字；
- 在 `analysis/README.md` 修正原本「相關高就懷疑自動增益」的說法：只有機台穩定運轉的片段，這個相關才有意義。

## 五、沒有驗證的

- 真實手機錄音：還沒有。這個工具就是為了做這件事。
- 臨時通道網站下載檔的實際格式：只從網頁程式看到下載網址帶 `take_id`，還沒實際下載過。工具用 ffmpeg 解碼，常見格式都能讀。

## 六、重要：臨時通道上的錄音網站沒有關掉手機的收音處理

該網站的前端開麥克風時只寫了 `getUserMedia({audio:true})`。瀏覽器的預設值會開啟三項處理：

- **降噪**：機台的穩態運轉聲正是降噪要去掉的聲音。
- **自動增益**：位準會跟著響度飄，三軌之間的大小無法比較。
- **回音消除**：會改變波形。

本儲存庫的錄音版本有明確關掉這三項（`feature/room-code-recording` 的 `frontend/src/capture.ts:22`）。

在這個網站修正之前錄的檔案：
- 能驗證對齊流程；
- 大小、相位、頻率的數字不能當作正式結果。

## 七、實錄步驟（建議）

1. **擺位**：三支手機從不同方向對著機台，記下各自的位置與距離。另外準備第四台裝置（筆電或手機）播放 `sync_chirp.wav`，放在三支手機中間附近。
2. **錄音**：
   - 三支手機在網站上統一開始錄音。
   - 開始後先安靜 10 秒（機台不動），再播一次嗶聲。
   - 開機，依計畫的工況（轉速、進給、ap、ae…）加工。
   - 停機後再播一次嗶聲，等 2 秒後統一停止。
3. **下載**：從網站「錄音結果」頁下載三個檔案，檔名註明 A／B／C。
4. **分析**：

```powershell
python -X utf8 analysis/offline.py run --a A.webm --b B.webm --c C.webm --out D:\cnc_offline\run1 --note "機台、S、F、ap、ae、麥克風位置"
```

5. **看結果**：先看「對齊判定」。
   - 通過：再看 `fig2_phase_*.png`（相位）與 `fig3_background_removal.png`（去背景）。
   - 不通過：把 `offline_report.json` 給我判讀。
