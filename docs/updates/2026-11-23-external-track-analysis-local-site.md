# 2026-11-23 更新：在本機把網站後端跑起來，讀地端寫入的結果

分支：`claude/external-track-analysis-v1`（PR #5）。接續 [`2026-11-23-external-track-analysis-on-main.md`](2026-11-23-external-track-analysis-on-main.md) 的「下一步」第 2 項。
狀態：**本機驗證通過。沒有改任何程式。正式站仍未驗證。**

## 一、做了什麼

先前只確認過「網站查詢用的 SQL 對著地端的資料跑得出正確內容」。這次把網站的後端和前端實際跑起來，從錄音到分析頁走一遍。

| 項目 | 內容 |
|---|---|
| 網站後端 | `backend.local`（API＋前端），只聽 `127.0.0.1:8011`；環境 `pg_test`：Python 3.12、FastAPI 0.162.4、uvicorn 0.54.0、PyAV 19.0.2、numpy 2.5.5、scipy 1.18.1、matplotlib 3.11.2 |
| 前端 | 用這個分支（已含 `main`）的原始碼重新建置：`tsc --noEmit` 沒有訊息，`vite build` 成功 |
| 資料庫 | 本機 PostgreSQL 18 的全新測試庫：public V1.2 → `backend/migrations` 001–005 → `deploy/track_analysis_writer_role.sql` |
| 地端 worker | 環境 `audio_preject`，用最小權限帳號 `track_analysis_writer` 連線 |
| 音檔 | 兩支真實的 Chrome 錄音（WebM／Opus，48 kHz 單聲道，37.14 秒與 37.26 秒），原樣切成 3 段與 4 段上傳 |

錄音這一段全部經由網站自己的 HTTP 與 WebSocket，沒有直接改資料庫：

建房（2 人）→ 加入 → WebSocket 認證、收音設定、麥克風、就緒 → 設定加工條件 → 開始 → 兩台回報已準備 → 倒數 → 兩台回報實際開始 → 上傳音段 → 停止 → 完成封存 → 內建分析自動完成。

封存後網站記錄的 SHA-256 和本機的原始檔案相同。

接著地端 worker 寫入三次：整段（`--session`）、5–15 秒區間（`--start 5 --end 15`）、批次（`--pending --once`）。

32 項檢查的內容：

- API 顯示的是地端那一筆，狀態 `completed`，`versions` 標明產生者。
- 最上層欄位：內建有的地端都有；9 個欄位的值和內建相同（含 `time_range`、`duration_seconds`、`completed_device_count`）。
- 內建的 16 個分析參數地端都有，除了版本字串之外都相同。
- 每一軌：`track_id`、順序、17 個欄位（含解碼後的總樣本數、`valid_range`）和內建相同。
- 每一張圖：網址指向地端那一筆、下載回來是 960×480 的 PNG；內建那一筆的圖也還讀得到。
- 權限：沒帶憑證 401；別的房間的憑證 403；同房間另一支手機讀得到。
- 在頁面上再按一次分析：網站回它自己原本那一筆，不重算；之後 API 仍顯示地端那一筆。

### 兩邊存下來的數值（真實錄音）

比的是「網站：PyAV 解碼＋內建計算」和「地端：ffmpeg 解碼＋地端計算」各自存進資料庫的矩陣。

| 區間／裝置 | 影格數 | Spectrogram 最大差（dB） | MFCC 最大差 | 時間軸、`valid_range` |
|---|---|---|---|---|
| 整段 A | 3710 | 0.0032 | 9.2e-5 | 完全相同 |
| 整段 B | 3722 | 0.0037 | 1.4e-4 | 完全相同 |
| 5–15 秒 A | 996 | 0.0018 | 3.1e-5 | 完全相同 |
| 5–15 秒 B | 996 | 0.0037 | 1.4e-4 | 完全相同 |

Spectrogram 的差異比「同一份樣本進去」時的 3.8e-6 dB 大。推測是兩個解碼器的樣本本來就有 1e-7 量級的差異（2026-11-20 量到 9e-8），在接近 −120 dB 下限的頻格被放大；沒有逐格確認。

## 三、過程中發現的事

1. **後端第一次啟動後在內建分析時當掉**（Windows 錯誤碼 `0xC06D007F`，位置是 `analysis_signal.py` 的矩陣乘法）。原因是我啟動時沒有先啟用 conda 環境，數值函式庫載到 Anaconda 主環境裡舊版的 `libiomp5md.dll`。把環境自己的 `Library\bin` 放到 PATH 最前面之後正常。這是啟動方式的問題，不是網站程式的問題。當掉時那筆內建工作停在 `running`；重啟後網站把它改回 `queued` 並做完，網站自己的復原機制有作用。
2. **同一個 session 會有不只一筆內建結果。** 每台裝置完成封存時網站都會排一次分析，而辨識碼包含當下的封存清單，所以 2 台裝置排了 2 筆，兩筆的內容都是 2 軌。查詢 API 取最新的一筆，不影響顯示，只是重複計算。這是網站那邊的行為，這次沒有改。
3. **分析頁上方的「等待地端分析：地端電腦開機並連線後會自動處理」不是這裡的聲道分析。** 那一行來自另一條工作佇列（`analysis_jobs`，離線對齊分析）。聲道分析已經完成時它仍然會顯示。
4. 第一版檢查把「版本字串不同」算成失敗（30/31）。版本字串本來就各自標示，是檢查寫錯；改成分開檢查之後 32/32。

## 四、還沒有驗證的

- **正式站**：部署的版本、PyAV 版本、以 `track_analysis_writer` 連線寫入，仍需要部署管理入口。
- 手機協定是用腳本照著做的，**不是真的手機瀏覽器在錄音**；瀏覽器端的錄音與上傳程式沒有執行。
- 只走了 Chrome 的 WebM／Opus 單聲道、2 台裝置。iPhone Safari 的 MP4／AAC、立體聲、3 台以上、缺檔或解碼失敗的來源，沒有在實際跑起來的 API 上走過（資料庫層的自動測試有涵蓋）。
- 網站自己的測試（`backend/tests/`、前端測試）沒有跑。
- 驗證用的腳本放在暫存資料夾，沒有收進儲存庫。
